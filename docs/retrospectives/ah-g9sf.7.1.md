## `npx prettier --write` reformatted six files in a repository that has no prettier — and this time it reached a reviewer

**What happened.** After adding `swim` to the `UnitMovement` test fixtures I ran
`npx prettier --write` over the seven files I had touched, to tidy the literals I had just edited by
script. This repository has no prettier — no `.prettierrc`, no `prettier` in any `package.json`, no
`format` script, nothing in `eslint.config.mjs` — so npx fetched it and reformatted at its own
defaults, rewriting pre-existing lines across the whole of each file. `pnpm run check:fast` passed
on all six legs throughout, so nothing caught it. The PR opened at **3,769 insertions / 1,466
deletions for about sixty lines of real change**: `UnitTableDock.test.tsx` showed 1,022 insertions
whose only substance was one line, `swim: { kind: "absent" }`. The cold-read reviewer's first and
largest finding was this, and it had to reconstruct the change by reading the new head because the
diff was unusable. Reverting the seven files to main and reapplying only the semantic lines by hand
brought the diff to 572/33.

**Why.** Established, and the same cause both earlier sightings named: `npx` silently installs a
tool the project does not declare, and with no config present applies its own defaults to whole
files rather than to the region edited. The gate cannot see it, because style here is enforced by
eslint's rules and not by a formatter.

**Cost.** About twenty-five minutes — a wasted cold read on an unreadable diff, the revert and
by-hand reapplication of seven files, an extra commit, and a delta round to confirm nothing semantic
was lost in the revert. The reviewer had to verify that by comparing test-name sets across the two
heads, which is work no reviewer should have to do.

**Prevent by.** The two earlier files each proposed a check for the implementer to run
(`ls .prettierrc*`, `grep -n prettier package.json`). That prevention has now failed three times,
because it relies on an implementer having read a retrospective it has no reason to open. Put it
where an implementer cannot miss it: `.cerebro/traps.md`, which `implement-bead`'s *Traps this
fleet has already paid for* tells every session to read — one line saying this repository declares
no formatter, that `npx prettier` will reformat whole files, and that `awk 'length > 100'` over the
touched files is the check that matches what the codebase actually does. A gate leg would be
stronger still: `check:fast` passing on a 3,700-line reformat is the reason this reached a reviewer
rather than being caught locally.

**Seen before.** `ah-dbw4` and `ah-lbd9.4` — same tool, same cause, same repository. Both caught it
themselves with `git diff` before pushing; this is the first sighting that reached a review, which
is what makes it worth a third file rather than a shrug.

## A doc comment containing `*/` made the generated TypeScript unparseable, and only eslint saw it

**What happened.** The plan's text for `MovementRules::swimming` cited a stale build artefact at
`apps/*/dist/ruleset*.json`, and I copied it into the Rust doc comment. ts-rs copies a doc comment
verbatim into a TypeScript block comment, so the `*` followed by `/` closed that comment early and
`packages/ruleset/src/generated/MovementRules.ts` stopped parsing. Neither `cargo test`,
`cargo clippy`, `pnpm run typecheck` nor `pnpm run check:generated` noticed: the only complaint was
`pnpm run lint`, as `16:31 error Parsing error: Property or signature expected`, and even that named
the file only when eslint was run directly in the package rather than through the workspace script.

**Why.** Established. `#[cfg_attr(test, derive(ts_rs::TS))]` re-emits the doc comment as
`/** … */`, and nothing escapes a `*/` sequence inside it. `check:generated` compares the committed
output against a fresh export, so a file that is byte-identical to what ts-rs produces passes even
when what ts-rs produces is invalid TypeScript.

**Cost.** About ten minutes to read a parse error that pointed at generated output, trace it to a
Rust doc comment, reword and regenerate.

**Prevent by.** A line in `.cerebro/traps.md`: a doc comment on any `ts_rs::TS` type must not
contain `*/`, so a glob like `apps/*/dist` is written without it. The comment in `rules.rs` now says
so at the site. Worth noting for a planner too — this one arrived from the plan's own prose, so
`plan-bead` quoting a path glob into a doc comment for an exported type is where it starts.

**Seen before.** None found — `grep -rn "block comment early\|Do not edit this file manually"
docs/retrospectives/` returns nothing.

## A PR that was born conflicting got no CI run at all, and I waited forty minutes for checks that could never arrive

**What happened.** `gh pr checks 1192` answered "no checks reported on the branch" for three
consecutive heads across forty minutes, while other PRs opened in the same window ran normally.
`gh api .../actions/runs?head_sha=<sha>` returned `total_count: 0` for every one of my heads, and
`.../commits/<sha>/status` read `pending` with zero statuses — so no run was ever scheduled, as
opposed to queued. `gh pr view 1192 --json mergeable,mergeStateStatus` then read
`CONFLICTING DIRTY`, with `headRefOid` equal to the head I had pushed, so the verdict was about the
current head and not a stale one. A rebase onto `origin/main` (two additive conflicts in
`newage_ruleset.rs` and `movement_ruleset.rs`, both sides appending tests) and a force-push
scheduled a full eleven-job run within seconds.

**Why.** Established as a correlation, and now on its second sighting: GitHub does not schedule a
`pull_request` workflow for a head it cannot merge, and says so nowhere the PR surface shows. The PR
was **unmergeable from the moment it opened** — three sibling `ah-g9sf` beads merged while this one
was being built.

**Cost.** About forty minutes of polling, split across two waits and a background command that
timed out at ten minutes still finding nothing.

**Prevent by.** `implement-bead`'s *Merging* section already carries the merge-state check, and
`ah-64wm` already asked for "no checks reported at all" to route to it. Neither placement catches
this case, because both are written as a guard after *a push that could have raced main* — and this
PR was conflicting at **open**, before any such push. The fix is to put the merge-state check at the
start of the CI wait unconditionally, not only after a racing push: in *The review loop*, where it
says to wait for CI once every finding is answered, and in the *Merging* bullets, read
`mergeable`/`mergeStateStatus` **before** the first CI wait of the bead as well. One
`gh pr view --json mergeable,mergeStateStatus,headRefOid` costs a second and would have replaced
forty minutes here and two abandoned passes on `ah-64wm`.

**Seen before.** `ah-64wm` — same symptom, same correlation with a `CONFLICTING` head, same
forty-minute order of cost, and its proposed prevention is the one this run shows to be
insufficiently placed.
