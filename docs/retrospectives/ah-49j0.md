# ah-49j0 — a refactoring bead raced three bug fixes into the function it rewrites

**What happened.** ah-49j0 rewrote `sharing_purse` (crates/core/src/orders/semantics.rs) because that function had taken three fixes in ten hours. While it was in review, three more beads merged into the same function: ah-ludc (#1456), ah-m2d9 (#1455) and ah-vusi (#1457). The PR went `CONFLICTING DIRTY` with five conflict hunks in `sharing_purse`. Each fix's intent had to be re-read and folded into the new settlement by hand. ah-m2d9's settled-tax reading was the one that needed new code. The merge then needed a second, follow-up review, and that review found the folded-in gate was untested.

**Why.** Established. Nothing in the bead graph links a `Refactoring:` bead to the open bug beads in the code it names. Its *Where* section listed `sharing_purse`, and ah-ludc and ah-m2d9 were bugs in exactly that function, filed from the same reviews that motivated the refactor. `bd ready` offered all of them to the fleet at once, so they were built in parallel against the old shape.

**Cost.** About 40 minutes: a squash and a rebase, a hand merge of five hunks, one follow-up review round, and one extra test pin. The fixes themselves were small and are now simpler, but each landed as a special case the refactor then removed.

**Prevent by.** When a `Refactoring:` bead names functions in its *Where*, the planner (or Forge, at filing) runs `bd list --status open` for beads whose text names those functions. It then wires `bd dep add <bug> <refactor>` or the reverse, so the two are not built in parallel. The place for that step is Forge's filing checklist in `.claude/agents/` (the architect definition).

**Seen before.** ah-t2pn.4: four sibling beads writing the same function, each merge leaving the next PR `CONFLICTING DIRTY`. That family had parent/child edges and still raced. This one had no edge at all.
