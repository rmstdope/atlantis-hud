## A timing guard went red because of work it was never meant to measure

**What happened.** The smoke guard "the interface is not blocked while the core reads a report"
crept up to 900ms on CI. The first pass at this bead (Nightcrawler) traced the figure to
validate_orders plus preview_orders, and treated it as a core regression in need of a full
performance pass. Profiling the browser showed those two calls were the reload's checks, not the
import's. Reopening the stored turn schedules them behind a 300ms debounce, and they fired inside
the sampling window that starts after "restored turn 72". With a 3s wait before the window, the
import alone blocked about 110ms under a 6x throttle. On CI it was 122ms (web) and 95ms (desktop
shell).

**Why.** The guard waits for the reload's parse (issue #34) but nothing waited for the work the
reload starts after that parse. As the checks grew, their cost drifted into a figure labelled as
the import's.

**Cost.** One hand-back and a navigator decision taken on the wrong premise ("real perf pass").
About an hour of native profiling before the browser profile showed which calls were in the window.

**Prevent by.** For a main-thread timing guard, log which core queries ran inside the sampling
window as well as the worst block. The adapter's `createQueryMethods` in
`packages/browser-core/src/webCoreAdapter.ts` is the one place every query crosses. Then a figure
that drifts names its contents, and the first person to read it does not have to guess.

**Seen before.** none found.

## The fast gate passed with a regenerated binding left uncommitted, and CI's rust job failed

**What happened.** A doc comment added to `Ruleset::items` changes the generated
`packages/ruleset/src/generated/Ruleset.ts`, because ts-rs carries doc comments into the
bindings. `pnpm run check:fast` reported `generated PASS` and printed "1 is not committed yet:
packages/ruleset/src/generated/Ruleset.ts". I staged the two files I had edited by name, so the
regenerated binding stayed out of the commit. CI's "Generated TypeScript bindings are committed"
step failed.

**Why.** The gate's `generated` leg now passes when the regenerated file only needs committing,
and reports that in a line inside the leg's log rather than in the summary line.

**Cost.** One CI cycle, and one of the bead's three fix attempts.

**Prevent by.** Put the uncommitted-binding warning in `scripts/runGate.ts`'s summary line, for
example `generated PASS (1 uncommitted)`. Or make the leg fail when a regenerated file differs from
`HEAD`. Either way, the line an agent reads would show it.

**Seen before.** ah-1wcw.3, ah-gdfe, ah-moq3: the same uncommitted regenerated bindings. Those
runs were red locally; this one was green locally and red only in CI.
