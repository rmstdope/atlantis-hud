## `git checkout -p` in a scripted Bash call hung for the full ten minutes

**What happened.** To prove three new regression tests were real covers, I reverted three read
sites, ran the suite, then tried to restore the file with
`git checkout -q -p crates/core/src/orders/semantics.rs 2>/dev/null; <python restore>; pnpm run check:fast`.
`-p` is interactive: it printed a hunk and waited for a keystroke that never came. The whole
compound command sat until the 600000ms `Bash` timeout moved it to the background, taking the
`check:fast` run in the same call with it. `2>/dev/null` hid nothing useful and the prompt went to
stdout, so the only symptom was silence.
**Why.** Established: `-p` was a slip for a plain path checkout, and the harness cannot distinguish
a tool waiting on a TTY from one doing slow work. The project's `CLAUDE.md` bans interactive `git`
flags (`git rebase -i`, `git add -i`) but names `-p` nowhere, and `-p` is the one that reads as a
narrowing flag rather than an interactive mode.
**Cost.** About ten minutes of wall clock, one abandoned gate run, and a `TaskStop`.
**Prevent by.** `implement-bead`'s *Waiting, without ending your run* already says a silent tool
call is indistinguishable from a hang; the missing half is the list of commands that produce one.
Adding `-p`/`--patch` to the interactive-flag list in the consumer `CLAUDE.md`'s **Git** section
would name it where it is looked for. In the meantime: restore a file with
`git checkout -- <path>` or `git restore <path>`, never `-p`, and never chain a long gate run behind
a command that could block.
**Seen before.** None found — `grep -rl "checkout -p" docs/retrospectives/` finds nothing.

## A plan's own increment boundary put a test in the increment before the behaviour

**What happened.** The plan placed `a_formed_units_flags_follow_its_own_block` in increment 2 while
stating increment 2 "changes no behaviour". The test asserts through `UnitSilver.taxes_by_flag`,
which only moves when increment 3 repoints the read sites, so increment 2 could not be committed
green on its own and increments 2 and 3 became one commit.
**Why.** Established by reading the plan: the assertion was deliberately routed through
`review_turn` (because a formed unit is built by `formed_units`, not by the test), and that route
necessarily crosses into increment 3's readers.
**Cost.** Small — a few minutes and one merged increment boundary, recorded as a deviation in the PR.
**Prevent by.** `plan-bead`'s increment section could ask that a test asserting through a surface be
placed in the increment that moves that surface. An increment that "changes no behaviour" cannot
carry a test that asserts one.
**Seen before.** None found.
