# ah-728m.2.2 — retrospective

## A plan that scoped out one of two paired readers shipped a self-contradicting tooltip

**What happened.** The plan's *Out of scope* gave the SILVER forecast to `ah-728m.2.3` and its
*Files to change* said "No changes are planned in `crates/core/src/orders/silver.rs`". Both are
defensible in isolation. But this bead made the ITEMS ledger pool a hex's `SHARE`d materials, and
the two columns meet in one hover:

```
Includes 36 SWOR this unit will produce. Production resolves last, so they cannot be spent this month.
This unit has materials for 16 swords, not the 39 its skill and tools could make.
```

Two false sentences, in the feature the bead delivers. Neither the plan's *User-facing decisions*
("no new hover sentence is introduced" — true, and beside the point) nor its *Known traps* saw it,
because the question is not "does this bead write copy" but "does this bead make existing copy
false". The second sentence was collateral of the same kind: a manufacturing output *can* now be
spent this month, by a later manufacturer or a BUILD.

Found by the review sub-agent, which ran the built application rather than reading the diff. Nothing
in the repository would have caught it: `crates/core/tests/silver_for_a_production.rs` exists
precisely to assert the two columns agree and had no sharing case, and `silver.rs`'s own comment
claims the invariant the change broke — *"`semantics::produce` reads exactly the same phase for the
ITEMS column, so the two surfaces answer one order identically"*.

**Why.** Established. `silver.rs` and `semantics.rs` derive one settlement twice by design, and the
plan scoped a change to one of them without asking what the other says about the same order.

**Cost.** A question to the navigator, then about ninety minutes: the seam, two review rounds on it,
and the tests. Cheap only because the review ran the app.

**Prevent by.** `plan-bead` should treat *"which other reader states the same fact to the user, and
does this change make its sentence false?"* as a question the plan answers explicitly, the way it
already answers "what does the user see". Concretely for this codebase: a plan touching the ITEMS
ledger's arithmetic names what `orders/silver.rs` says about the same order, or says why nothing
does. The mechanical cue is a `crates/core/tests/*.rs` file whose whole purpose is that two surfaces
agree — if the bead changes one of them, that file needs a case.

**Seen before.** `ah-ycuj`, `ah-abwx`, `ah-lu0f.2`, `ah-dxfd.1`, `ah-gdd3.2` — the ITEMS/SILVER pair
drifting apart, which is why the corpus test and that comment exist at all. This is the first
sighting where a *plan* scoped the drift in rather than an implementer introducing it.

## My regression test passed against the code it was written to catch

**What happened.** `a_spend_never_nets_off_an_output_credited_after_it` was written for a real defect
the review found (a phase-blind netting). It built its hex with the module's `region(...)` helper,
which leaves `products` empty — so the lumberjack in the fixture produced nothing at all, there was
no output for the netting to get wrong, and the asserted `5` was just `20 - 15` under any rule. The
review checked out the previous head, grafted the committed test in unmodified, and it passed.

**Why.** Established: I asserted a number that was right for the wrong reason and did not run the
test against the old behaviour. The fix — a region that yields wood — makes it fail with `left: 15,
right: 5`, which I then verified in both directions.

**Cost.** One review round, about ten minutes, plus the round that found it.

**Prevent by.** Nothing new is needed — `implement-bead`'s TDD flow already asks for RED first, and
this test was written after the fix, which is exactly the gap. What *is* worth adding, because this
is now the eighth sighting: for a test written after its fix, run it against the old behaviour
before committing it (revert the one expression, watch it fail, restore). I did that for the two
tests I wrote afterwards and it took under a minute each.

**Seen before.** `ah-gdd3.2` (which lists `ah-ycuj`, `ah-qled.4`, `ah-3mwm`, `ah-enik`,
`ah-lu0f.3`, `ah-dlao` and calls this "the strongest evidence in the directory that something needs
fixing rather than tolerating"), and `ah-3rxk`. Eight sightings; still caught by a reviewer rather
than by the implementer, every time.

## Moving a function detached its doc comment — twice, in one bead

**What happened.** Clippy's `too_many_arguments` made me move a new helper; the move put it between
`pub fn workforce_for`'s rustdoc and `workforce_for` itself, so a public function lost both its
documentation and its `#[must_use]` and the private one was documented as being about workforces.
Fixing *that* by moving the helper again left its own doc comment behind, so it became the first
paragraph of the neighbouring function's. Both caught by the review; neither by me.

**Why.** Established: `cargo build`, `cargo clippy` and `cargo fmt` are all silent when a doc comment
attaches to the wrong item, and a diff of a moved function shows the comment as unchanged context.

**Cost.** Two review rounds' worth of a finding each, perhaps ten minutes.

**Prevent by.** When a function moves past another one, read the four lines above *both* landing
sites in the resulting file rather than in the diff. There is no check to add: this is invisible to
the whole gate, which is why it is worth writing down a third time.

**Seen before.** `ah-2a96` (a removal stranded a helper's `/** … */` above the next test) and
`ah-3mwm` (a test inserted between a doc comment and its body). Third and fourth sightings.
