# ah-84b1 — retrospective

## The warning passed every test and never showed in the app

**What happened.** The first build (PR #1671) merged green with six integration tests. It failed
verification: in the web shell, Two of Seven (12878)'s template block plus `GIVE 0 30 SWOR`
showed no warning. Every test wrote the discard as the unit's only order (`unit 12878\nGIVE 0 30
SWOR`). The verification note then blamed the request options a remembered map brings. Its own
core reproduction had put the discard straight under `unit 12878`, before the template's lines,
so it emitted the warning and pointed away from the real cause.

**Why.** The guard read the walk's unit-wide `items_unknowable`. A named item the unit does not
hold also sets that flag (`transfers::Selection::Unresolved`), although nothing moves. This
faction's template opens every block with `@give 0 all hors`, `@give 0 all fur` and the like, so
any real block silences the check. A bare-orders test can never meet that.

**Cost.** One verification round at P0, a reopen, and about an hour of this rework. Most of it was
spent ruling out the suspected request options before a Playwright walk showed the failure:
replacing the block made the warning appear, appending to it made it vanish.

**Prevent by.** For a check that reads the transfer walk's state, add one integration test that
places the order after the unit's own block from the fixture's `Orders Template`, through
`validate_orders_request`. The template is the orders a player actually starts from.
`a_discard_from_shared_stock.rs::the_template_s_own_discards_do_not_silence_the_warning` is the
pattern. A planner writing *The test plan* for such a check would name it there.

**Seen before.** Same family: `ah-256d` (a fixture's own template changed what the walk computed)
and `ah-5znb` (core run on the fixture's template gave different figures from the bare case). Both
found the template mattered after the fact.
