## The host the plan told me to fetch fixtures from was DNS-sinkholed

**What happened.** The plan's first step is fetching two ~300 KB fixtures from
`https://atlantis-newage.com/api/worlds/<world>/game/database`. Every attempt failed:
`node -e 'fetch(...)'` with `ECONNRESET` / "Client network socket disconnected before secure TLS
connection was established", and `curl` with
`(35) LibreSSL SSL_connect: SSL_ERROR_SYSCALL`. `nslookup atlantis-newage.com` showed
`canonical name = sinkhole.paloaltonetworks.com` — a network filter, not a flaky endpoint.
`https://atlantis-pbem.com/data` answered 200 throughout, so it did not read as a connectivity
problem. `dangerouslyDisableSandbox` made no difference; the block was outside the harness. The
navigator lifted it and both fetches then returned 200 in one call.

**Why.** A Palo Alto DNS filter on the machine's network classified the host. Why it did is not
established.

**Cost.** About ten minutes of diagnosis and one navigator question — the bead was blocked outright
until a person answered, since a fixture cannot be invented.

**Prevent by.** A plan whose first increment depends on fetching from a host **not already used by
this repository** should say so in *Known traps* and name the one-line reachability check
(`nslookup <host>`, or `curl -sSI -m 10 https://<host>/`) to run before the worktree is prepared. A
`sinkhole.paloaltonetworks.com` CNAME is the answer that distinguishes "filtered here" from "the site
is down", and neither `fetch` nor `curl` says it. This applies to `ah-77j1.2` and `ah-77j1.3`, which
fetch the New Age rules pages from the same host.

**Seen before.** None found — `grep -rln "sinkhole" docs/retrospectives/` matched nothing.
