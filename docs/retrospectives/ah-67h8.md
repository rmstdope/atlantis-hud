## A shipped smoke test was passing by accident of layout, and this bead's diff moved the layout

**What happened.** `tests/smoke/magic-graph.spec.ts:66` "the two views share one current skill"
went red on this branch: light `CRRI` in the graph, toggle to Branches, `toBeInViewport()` →
`viewport ratio 0`. The instinct was that the tint had broken the toggle. It had not. Instrumenting
the page showed the branch body is a CSS multi-column container 1022px wide with a `scrollWidth` of
3042 — it scrolls sideways — with `CRRI` sitting at x=1160 and `scrollLeft` still 0. Nothing had
scrolled, and nothing ever had: `MagicTreeDialog`'s scroll effect is keyed on `[highlighted]`, and a
view toggle swaps the body rather than remounting the dialog, so the effect never runs for the cards
that have just appeared. The test passed for two beads because `CRRI` happened to fall inside the
first visible columns with no scrolling at all.

**Why.** Established. The effect's own comment claims the opposite — "Effects run on mount too,
which is the whole of why toggling back to Branches lands on the skill the graph was lighting" —
which is true of a mount and false of this toggle. Adding a chip to nearly every row grew the body
past three screen-widths and pushed `CRRI` out of the accidental window. The effect now keys on the
view as well, and scrolls `inline: "center"` because the inline axis is the one that actually
scrolls here.

**Cost.** About forty minutes: a full 4.8-minute web smoke run to find it, a second to reproduce it
alone, a throwaway instrumented spec to get the numbers, and the reasoning to tell "my change broke
this" from "my change stopped this passing by luck".

**Prevent by.** A `toBeInViewport()` assertion on an element inside a scrollable container proves
nothing on its own — it holds whenever the element happens to be on screen. Where a test means "the
application scrolled to this", it should assert the container moved: read `scrollTop`/`scrollLeft`
before and after, or assert a non-zero one. `implement-bead`'s *Traps this fleet has already paid
for* has a neighbouring entry about accessible names being a shared namespace; this is the same
shape — a spec in a file with nothing to do with the change, reddened by a layout the change grew.

**Seen before.** `ah-e4v` — a test that passed against a build the navigator had just watched fail,
for the same underlying reason: the assertion did not actually constrain the thing it named.

## An SVG `<line>` is never `toBeVisible()`, however plainly it is drawn

**What happened.** The graph's per-state bar is a vertical `<line>` (`x1 === x2`). The new smoke
spec asserted `await expect(page.getByTestId("magic-graph-bar-FORC")).toBeVisible()` and failed with
`33 × locator resolved to <line …> - unexpected value "hidden"`. The element was on screen, correct,
and painting; its bounding box is zero-width, and Playwright's visibility check reads that as
hidden.

**Why.** Established: Playwright treats a zero-area bounding box as not visible, and a
zero-thickness geometric primitive has one however wide its `stroke-width` renders.

**Cost.** One 35-second smoke run and the read of the failure. Small, but the failure text names
the element and says "hidden", which invites looking for a rendering bug that is not there.

**Prevent by.** For an SVG hairline — a `<line>`, or any `<path>` with no area — assert
`toHaveCount(1)` and `toHaveClass(/…/)` rather than `toBeVisible()`. Worth an entry in
`.cerebro/traps.md` beside the existing WebKit-clipped-text one, which is the same class of
fact: a driver's answer about a shape is not the same as what a person sees.

**Seen before.** `ah-2r3` — settlement `<g>` elements rendering with a real but collapsed bounding
box, found the same way and costing rather more.
