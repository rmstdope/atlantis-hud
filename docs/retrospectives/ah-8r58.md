## The fixed tests went red after the review, with the fix still in the tree

**What happened.** After the cold-read reviewer reported, I added two PRODUCE tests and reran the
test file: the two BUILD tests that had passed before the review now failed on the very assertion
the fix makes true (the builder has no preview row). `git diff HEAD` showed the fix in place.
Running the committed test file alone failed the same way. `touch crates/core/src/orders/effects.rs`
made cargo recompile `atlantis-hud-core`, and all four tests passed.

**Why.** Not established for certain. The reviewer reported that it ran the new tests "at the
commit before the fix, 8036ee87" to prove they reproduce the bug. If it did that by putting the old
`effects.rs` into this worktree and then restoring it, rather than in a separate tree, the restored
file's modification time is older than the library cargo had just built from the old source.
Cargo's fingerprint then judges the library fresh, and every later run in this tree tests the
pre-fix code.

**Cost.** About ten minutes, and a moment of believing the fix had regressed. Had I not compared
against the committed file, a passing fix could have been "re-fixed", or a red reported as a CI
flake.

**Prevent by.** `.cerebro/cerebro/agents/reviewer.md`: when the reviewer proves a reproduction test
fails before the fix, it does so in a throwaway `git worktree add` of its own (its own `target/`),
never by checking out older files in the producer's tree. And in `fix-bug`: after a review
sub-agent returns, the bugfixer's first test run forces a rebuild of the touched crate (`touch` the
changed source) before trusting a red.

**Seen before.** No. `ah-g9sf.7.1` records a stale build artefact cited by a plan, a different
mechanism.
