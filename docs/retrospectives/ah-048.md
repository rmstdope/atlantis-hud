## The plan's "is a fleet" test was not one, and its own trap is what proved it

**What happened.** The plan named `movement::mode::parse_fleet_kind(kind).is_some()` as the test for
"this structure is a hull", and stated the consequence as a known trap: *"a unit in a Fort follows
nothing, and using `structure_id.is_some()` as the test would have every garrison follow whoever in
the building wrote a MOVE."* I wrote `a_unit_in_a_building_follows_nothing` against Building [2], a
Fort holding two units, and it failed with the plan's implementation in place — the Fort's second
occupant followed the first one's MOVE. `parse_fleet_kind` is syntactic: its last line is
`Some(vec![(trimmed.to_string(), 1)])`, so **any** single-word kind reads as one hull of that name,
`Fort` included. The real test is the one `trace_move` itself applies before it draws a unit
sailing — a hull whose speed can be *priced*, from the server's stated `MaxSpeed:` or from the
ruleset — so `steps_followed_by` takes the ruleset and uses `fleet_speed(structure, ruleset)`.

**Why.** `parse_fleet_kind`'s own doc comment says so plainly ("Whether a kind actually names a hull
is a question for `parse_fleet_kind` to answer syntactically; whether that hull is one the ruleset
can price is a separate question"), on `fleet_of` two functions above it. The plan quoted the
function without that sentence.

**Cost.** Small, and only because the plan wrote the trap down: one RED cycle, about ten minutes,
and no rework beyond a parameter. Had the plan named the trap without a test for it, the bug would
have shipped as "garrisons follow the unit that wrote a MOVE" — a wrong route drawn confidently,
which is the same class of defect ah-048 exists to fix.

**Prevent by.** When a plan names a predicate function by name, read that function's doc comment
before using it — and write the trap the plan states as a test *before* the happy path, since it is
the trap that discriminates between two candidate predicates. Both halves happened here by luck of
ordering rather than by rule.

**Seen before.** ah-goz, ah-u4e.3, ah-a2k.2 — each a plan whose detail had drifted from what the
code actually said. This is the fourth.

## A blanket string replace over a test file double-wrapped its call sites, and every test still passed

**What happened.** `trace_orders_for_remembered_report` now takes the whole orders document, so the
acceptance tests in `crates/core/tests/movement_trace.rs`, which passed a bare block, needed a `unit
<id>` line. I added a `document(unit_id, orders)` helper, wrapped it into the file's `trace()` helper
— and then a Python string replace over the same file also wrapped five *call sites*, producing
`trace("18642", &document("18642", "MOVE N"))` (double) and
`&document("18642", &document("18642", "MOVE N"))` (nested). The whole suite went green: two
consecutive `unit 18642` lines simply re-select the same unit, so nothing asserted was affected.
Copilot's review caught all five.

**Why.** The replace matched on the order string (`"MOVE N"`), which appears both inside the helper's
own call and at every call site. Nothing distinguished them, and the tests could not: the defect was
in the *inputs* to tests whose assertions were about something else.

**Cost.** One review round and one CI cycle — the review had to land before it was known, and the fix
plus this retrospective is a second push. About twenty minutes, most of it waiting.

**Prevent by.** When a signature change is absorbed by a test file's own helper, change the helper
**only**, then `git diff` the file and read every hunk outside it — a call site that also changed is
a sign the replace was too broad. A blanket replace over a file that has both a helper and call sites
in it needs the diff read, because a green suite is not evidence here: nesting a document changed the
input without changing any answer.

**Seen before.** ah-v82 — also a blanket sweep, also a defect a clean grep could not see.
