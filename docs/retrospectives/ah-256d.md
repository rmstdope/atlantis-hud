- **Implementer:** Storm
- **Date:** 2026-08-29
- **PR:** #799

## Every ITEMS figure in the new corpus fixture was silently wrong, twice, for two unrelated reasons

**What happened.** The plan's increment 3 said to build the acceptance test on
`crates/core/tests/production_after_a_gift.rs` and "write the six `PRODUCE` orders that turn 42
actually ran". Following that literally — the report's own orders template, plus the six orders —
made every ITEMS figure exactly **twice** its settled share (32, 40, 32, 68, 18, 12 against 16, 20,
16, 34, 9, 6), while the SILVER half of the same rows was already correct. The template
(`neworigins-3.0.0-g3-f42-t42.rep:2746` onwards) already carries `@PRODUCE IRON` and one line each
for the other four, so each unit had two `PRODUCE` intents: the settlement counts a unit's first one
and no more, but `semantics::produce` runs per intent and credits both.

Dropping the appended orders and using the template alone then made four of the six read **0**, and
`assert_eq!` reported it as "the ITEMS column for unit 1795 producing IRON: 0" — which reads exactly
like the settlement zeroing the run. It was not. The template also carries
`GIVE ... ALL <the same goods>` for `1795`, `2693`, `3826` and `7671`, each of which holds precisely
what it produces, so the month's net item change is zero — and
`preview_orders_for_remembered_report` skips a unit whose `changes` are empty
(`crates/core/src/orders/effects.rs:383`), so those units are not in the response at all and
`map_or(0, …)` answers 0 for a unit that was never there.

**Why.** Established for both halves. The first is the pre-existing per-intent double-count the plan
itself names under *Out of scope* (`ah-o7td`) — correctly identified as not this bead's to fix, but
not connected to the fixture the same plan asked for. The second is `effects.rs`'s empty-changes
skip, which is right for the interface and invisible to a test that reads the response by
`find(...).map_or(0, ...)`: a missing unit and a unit that produced nothing are spelled the same
way.

**Cost.** About twenty-five minutes and three debug cycles, all after the implementation was already
correct — the SILVER column had the right six figures throughout, which is what eventually told me
the fault was in the fixture rather than in the settlement.

**Prevent by.** Two specific things.

- A plan that asks for a corpus fixture driving orders on a committed report should say whether that
  report's own template already carries the orders under test, and say which document the fixture is
  to use. `plan-bead`'s *Increments* section is where that belongs, beside the fixture it names.
- A helper reading a unit out of `preview_orders_for_remembered_report`'s response must
  `expect` the unit rather than `map_or(0, …)`. Absent is not zero, and a test that conflates them
  reports a wrong number instead of a missing row. The same shape is in
  `production_after_a_gift.rs`'s own `items_column_produced`, which is where this fixture copied it
  from — it is safe there only because that fixture's unit always has a net change.

**Seen before.** `ah-ycuj` records the neighbouring fact that no committed fixture's orders template
contains a `PILLAGE` order; this is the opposite failure — a template that contains the order under
test when the fixture assumed it did not. None found for the empty-changes skip.
