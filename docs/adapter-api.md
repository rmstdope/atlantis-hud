# Adapter API: the boundary between the core and the shells

The Rust core is one crate; two shells cross it, and one TypeScript boundary describes both.

- **The core's declared queries**: the stateless queries both shells answer alike, declared once in
  `crates/core/src/queries.rs` (ah-w83n). Each crosses the desktop through the one `query` Tauri
  command and the browser through the one `query` wasm export, and reaches TypeScript as a method of
  the generated `CoreQueries` type. See *Adding a query*.
- **Desktop**: `#[tauri::command]` — on core-tauri's own `command_*` functions for 29 of the 37
  commands (`query` among them), and on eight thin wrappers in `apps/desktop/src-tauri/src/main.rs`
  for the games-root commands that need the app handle (to resolve where this installation keeps
  its games).
- **Web**: the 21 `#[wasm_bindgen]` exports of `crates/core-wasm` (`query` among them), plus an
  IndexedDB store for what the core itself holds no opinion about (`packages/browser-core`).
- **TypeScript**: one typed `CoreAdapter` interface (`packages/core-client/src/index.ts`), which
  extends the generated `CoreQueries`; `TAURI_COMMANDS` and `createTauriAdapter`
  (`packages/core-client/src/tauriCommands.ts`) build the desktop transport from a single table, plus
  one method per declared query from `createQueryMethods` (`packages/core-client/src/queries.ts`); `createWebCoreAdapter`
  (`packages/browser-core/src/webCoreAdapter.ts`) is the web transport; `createCoreClient` adds the
  two ergonomic signatures (`exportMap`/`knownMap`'s JSON stringification) that `CoreClient`
  carries over `CoreAdapter`, and nothing else.

## Core contract (`EngineInfo`)

```json
{
  "id": "atlantis",
  "name": "Atlantis PBEM",
  "rulesetVersion": "4.0",
  "maxFactionCount": 128
}
```

Map topology is intentionally omitted from this payload because it is a fixed game invariant (always hex).

## Movement calls

Both adapters expose the same two movement entry points, each delegating to one shared core
function so the desktop and the browser cannot drift apart. The report travels as raw text, which is
the key the core's parse cache remembers it under.

- `plan_route` (Tauri) / `plan_route_state` (WASM) / `CoreClient.planRoute`:
  `(ruleset_json, raw_report, remembered_json, unit_id, destination)`, all strings, →
  `RoutePlanResponse { plan, problem, risk, fullyModelled }`. A route that cannot be planned
  resolves with a named `problem`; only an unusable ruleset or unreadable memory rejects.
- `trace_move_orders` (Tauri) / `trace_move_orders_state` (WASM) / `CoreClient.traceMoveOrders`:
  one `request: TraceMoveOrdersRequest { rulesetJson, rawReport, rememberedJson, unit, ordersDocument,
  mapJson, passagesJson }` → `MoveOrderTraceResponse { path }`. `unit` is a `UnitRef { regionId, unitId, arrivingFrom }`; the core
  traces it from `arrivingFrom ?? regionId`, the hex it set out from, since a new unit's `new-<n>` is
  unique only inside the hex it was formed in. Traces the last readable MOVE/ADVANCE line in the unit's
  written orders across the remembered map, extrapolating geometrically past everything known and
  guessing unknown terrain from the previous hex. `path` is `null` when there is nothing to draw
  (no movement order, no such unit, or an unknown origin); `path.months` is empty and `path.mode`
  `null` when the unit's speed is unknown (overloaded or unstated); `path.blockedFrom` is the
  index of the first step the game would refuse (a walker entering the sea), or `null`. Rejects
  on the same two grounds as `plan_route`.

The Tauri commands take snake_case argument names verbatim (`rename_all = "snake_case"`); the
TypeScript Tauri adapter (`TAURI_COMMANDS`) passes them explicitly rather than translating. Since
`ah-wxk.1` the commands are core-tauri's `command_*` functions under the `tauri` feature, renamed
to their bare names, except the eight games-root ones the shell wraps.

## Order checks and the preview

The order checks, the preview and the movement trace each cross as one request object rather than as
positional arguments (`ah-t8c4`).

- The `validate_orders` query / `CoreClient.validateOrders` takes a `ValidateOrdersRequest`, and the
  `preview_orders` query / `CoreClient.previewOrders` a `PreviewOrdersRequest`, each as its one
  positional argument. Both are generated by ts-rs from `crates/core/src/orders/request.rs`;
  `TraceMoveOrdersRequest` lives in `crates/core/src/movement/request.rs`.
- The fields inside a request travel camelCase, as the struct's own serde names: over the `query`
  command for the two declared queries, and as `trace_move_orders`'s one `request` argument for the
  trace. The WASM side reads the object with `serde_wasm_bindgen`.
- **Adding an input** is a field on the request struct, a line in its core builder
  (`validate_orders_request`, `preview_orders_request`, `trace_orders_on_map`), and the AppShell call
  site that fills it in. Neither shell assembles check options of its own.

## Map export

One entry point, shaped like the movement calls and for the same reason: the file a player trades
with an ally has to come out identical whichever shell wrote it.

- The `export_map` query / `CoreClient.exportMap`:
  `(raw_report, remembered_json, request_json)` → the file's whole text.
  `request_json` is a serialized `MapExportRequest { level, fromX, fromY, toX, toY, content }`,
  where the corners are inclusive and may be given in either order, and
  `content { structures, units, advancedResources }` says what to write beyond the region economy,
  markets and exits every export carries. `CoreClient.exportMap` takes the request as an object and
  serializes it.

  The output is report-shaped: comment lines naming the rectangle and the content, the report
  header for the player's own faction and turn, then one region block per visited hex in the
  rectangle, written in the syntax `crates/core/src/report/region.rs` parses. A hex last seen in an
  earlier turn is preceded by `; last seen turn N, M turns before this export`. The current report
  wins wherever it and the remembered map describe the same hex.

  Rejects when the request or the remembered regions cannot be read. A rectangle covering nothing
  visited resolves with a header and no regions.

## Adding a query

A query that needs nothing from either shell - no database, no games directory - and whose
parameters and answer are ts-rs bindings is declared once, and arrives on both shells from there:

1. The core function that does the work, wherever it belongs in `crates/core`.
2. Its entry in `core_queries!` in `crates/core/src/queries.rs`: name, typed parameters, answer type
   and a body that calls step 1, answering `Result<_, String>`. The doc comment becomes the
   TypeScript method's.
3. `cargo test -p atlantis-hud-core --lib export_bindings_`, which regenerates
   `packages/core-client/src/generated/CoreQueries.ts` beside the other bindings.
4. The caller, through `CoreClient` like any other method (`client.shelterSeats(...)`).

Nothing in core-tauri, the desktop shell, core-wasm, either TypeScript adapter, the adapter tests or
the native sweep changes. What holds the two shells to the declaration:

- **The generated file is current** — `pnpm run check:generated`.
- **Both shells answer every declared query** — `tauri_adapter_answers_every_declared_query` in
  core-tauri, `coreQueries.wasm.test.ts` against the real WebAssembly build, and over real IPC the
  native binding spec's every-query loop. Each asks for every name in the declaration and accepts
  only an answer or an argument refusal.
- **Both adapters route every declared query** — `index.test.ts` (desktop, `invoke("query", …)`)
  and `webCoreAdapter.test.ts` (browser, `wasm.query(…)`), both iterating `CORE_QUERIES`.

Arguments cross as a positional array, `{ name, args }` on the desktop; a query without parameters
ignores whatever it is sent.

## Adding a command

For anything shell-specific - storage, the games directory, an app handle - or a query whose types
are not yet ts-rs bindings:

1. The Rust function: a `#[tauri::command(rename_all = "snake_case", rename = "…")]` method in
   core-tauri (or, if it needs the app handle, a wrapper in `main.rs`), plus a
   `#[wasm_bindgen]` export in `crates/core-wasm` if the web needs it too.
2. The `CoreAdapter` method, in `packages/core-client/src/index.ts`.
3. The `TAURI_COMMANDS` row, in `packages/core-client/src/tauriCommands.ts` — the command name and
   its argument keys, in parameter order.
4. The `createWebCoreAdapter` method (and the `CoreWasmModule` member it calls through), in
   `packages/browser-core/src/webCoreAdapter.ts`, if step 1 added a wasm export.
5. The `SWEEP` row, in `tests/native/sweep.ts`.

What catches a missing step, so a slip is a failure on the machine that made it rather than a
surprise later:

- **Step 2, 3 or 4 missing or of the wrong arity** — `pnpm run typecheck`: `TAURI_COMMANDS` is
  typed as a mapped tuple over `CoreAdapter`, so a missing method, an extra one, or a row of the
  wrong arity is a compile error.
- **A wrong argument key, an unregistered command, a `SWEEP` row naming a key the command does not
  have, or a wasm export the browser type does not name (or vice versa)** — `pnpm test`
  (`scripts/tauriCommands.test.ts`'s live lockstep), on every machine.
- **The wire itself** — CI's `native` job, the one place a real IPC round trip runs.

## Trust

Neither adapter re-validates what the core sends back: the Tauri wire is Rust's own serde output,
and the wasm wire is our own code, so both are typed at compile time instead of re-checked per
call. `invoke<T>` (desktop) and the `coreWasm.ts` cast (web) are the two points where that trust is
declared; `CoreAdapter`'s own types are ts-rs-generated from the Rust core where such types exist
(`ah-164.2`), so the two sides cannot describe the payload differently by accident.
