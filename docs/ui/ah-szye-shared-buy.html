ah-szye round 2 — the engine's own BUY rule, and the one thing left to decide

Round 1 offered three ways of splitting a short purse between competing buyers. The engine source settles that: for BUY it does not split at all. GetBuyAmount sizes every unit's order against the full, undecremented shared pool in a first pass; DoBuy consumes in a second pass, and ConsumeShared has no failure path — when the money runs out the loop simply ends, silently, with no error and no negative balance.

GetBuyAmount   // pass 1: pool NOT decremented between units
    if (o->num * m->price > u->GetSharedMoney())
        o->num = u->GetSharedMoney() / m->price;
DoBuy          // pass 2
    u->ConsumeSharedMoney(temp * m->price);   // runs dry silently

So the rule to model is: each BUY line is capped at (its unit's own silver + the whole region's shared pool), and by nothing another buyer did. No buyer is ever cut on account of another. That is a real cap — it bites whenever one line alone outruns the purse — and it needs no ordering rule and blames nobody.

Question W — the hex is overdrawn, but the engine will pay out anyway. Say so, or stay quiet?

Only about scene 2: a pooled silver shortfall whose whole overdraft comes from BUY lines the engine will fulfil regardless. Every other pooled shortfall — STUDY, PRODUCE inputs, maintenance, a mixed hex — is unaffected whichever is chosen; those consumers do decrement the pool and do fail.
