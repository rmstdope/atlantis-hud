Round 3 drew Export… on the Army strip, and that is not in doubt. The question is whether the header's existing Export ▾ menu also carries it. Today that menu holds three items and knows nothing about Armies; the strip only exists while an Army is the source in the units dock.

Q3 — the mage's combat spell

The simulator reads a combatSpell per unit, and in a battle it matters a great deal. Your reports do carry it — Combat spell: fire [FIRE]. appears on your own units, and never on anyone else's. But our parser recognises that section only well enough to keep it out of the skill list; it stores nothing. Carrying it into the file means changing the Rust parser, the type it generates, the snapshot an Army persists for each member, the stored schema, the web database version and the backup format — all of which ah-1mpx.1 settled and shipped.

Option 1 — leave it out now, file it as its own bead — rejected
  • This bead stays what it says on the tin: a dialog and a serialiser.
  • The storage change lands once, with the battle-roster work that also wants to write to a member's snapshot.
  • Until then a mage exports as a man with a staff. The simulator will fight the battle without the fire.
  • The dialog would say nothing about it — unless you would rather it did.
Option 2 — do it in this bead — chosen
  • The first exported file is already right for a faction with mages in it.
  • The bead grows past a small increment: Rust parsing, a regenerated type, a schema migration, a database version bump and the backup.
  • It reaches back into shipped storage, which is where a mistake costs a person their saved Armies.

Q4 — what the header says afterwards

Round 3 settled the one-Army case: the dialog closes and the header status line reads exported Northern Host. With two Armies it has to say something else. On the desktop you picked the folder yourself, so the line is a confirmation rather than directions; in a browser the file simply lands in Downloads.
