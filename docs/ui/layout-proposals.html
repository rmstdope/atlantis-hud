Issue #17 · Basic UI for the app

Three layouts for the Atlantis HUD workspace

All four carry the same six widgets required by the issue — report loading, hex map with a layer bar, selected-hex info, a unit table, unit detail, and a per-unit orders editor. They differ in how those widgets are arranged and how the eye moves between them. Every screen below is drawn with real data from a live turn report, at true density.

01 — Classic Commander 02 — Three-Column Workbench 03 — Map-First Inspector 04 — Docked Inspector Comparison

This is the shape of the modern client in your fourth screenshot and of Atlantis Little Helper.

Why this one

  • Matches the muscle memory of all four reference clients you linked.
  • The unit table gets the full window width, so faction, men, silver, skills and items all fit without truncation.
  • Map keeps the largest contiguous area of any of the three.
  • Orders sit directly beside the table you pick the unit from — shortest path for the app's core loop.

Trade-offs

  • Report loading lives behind a button in the app bar rather than as a persistent panel.
  • The bottom dock costs vertical space the map would otherwise use.
  • Region panel needs internal scrolling on dense hexes.

Handheld

  • Rail and dock collapse into a bottom sheet with segmented tabs: Region / Units / Unit / Orders.
  • Map stays full-bleed above the sheet.

Strengths

  • All six widgets permanently visible — nothing is ever a click away.
  • Report loading is a first-class panel with turn history, closest to the issue's "loading/merging" wording.
  • Left-to-right reading order matches the task: turn → place → actor → orders.
  • Simplest layout to make resizable and to unit-test.

Trade-offs

  • Two side columns squeeze the map to roughly half the window.
  • The unit table is narrower, so items must be dropped or truncated.
  • Least like the clients your players already use.

Handheld

  • Columns stack into a single scroll; map pinned at top.
  • Maps most directly onto a narrow viewport of the three.
03

Map-First Inspector

The map is the application. It fills the entire window edge to edge, and the widgets float above it as dismissible glass panels — reports and units on the left, an accordion of region, unit and orders on the right. Collapse both and you get a full-screen map; the same drawers become bottom sheets on a phone.

Strengths

  • The map gets the whole window — by far the best for scanning a large world.
  • Collapsing both drawers gives a genuine full-screen map with no layout reflow.
  • Cleanest path to a good phone and tablet experience: drawers become sheets.
  • Most contemporary look of the three.

Trade-offs

  • Panels cover the map they describe — the hex you selected can end up underneath a drawer.
  • Unit table is narrow; only 3–4 columns fit.
  • Region info is collapsed by default, so it costs a click.
  • Most complex to build and to test: z-order, focus traps, collapse state.

Handheld

  • Native fit — the drawers are already the bottom-sheet pattern.
04

Docked Inspector

Recommended

Proposal 03's full-bleed map, rebalanced. Report state is promoted out of a floating card into the solid application header where it belongs. The unit table becomes a screen-wide dock along the bottom, as in 01, so it gets the horizontal room the columns actually need. Region sits alone on the left; unit and orders pair up on the right. Every one of the four panels collapses to a title strip, so the map can be opened right up.

What it takes from each

  • From 03: full-bleed map, floating glass panels, collapse-to-reveal.
  • From 01: screen-wide unit table with room for every column — here it even fits a Structure column the others could not.
  • New: report state lives in the header as persistent status rather than as a panel competing for space.

Strengths

  • Best balance of the four: full map and a full-width table.
  • Report info is always visible but costs no map area.
  • Left/right split keeps region reading separate from the unit-and-orders working pair.
  • Collapse state is per-panel, so you can keep just orders open while scanning the map.

Trade-offs

  • Panels still overlay the map; the selected hex can sit under the bottom dock on a short window.
  • Four independent collapse states are more to persist and more to test than a fixed grid.
  • Loading a report is a button, not a drop target you can always see — drag-and-drop onto the whole window covers this.

Handheld

  • Left and right panels become one bottom sheet with Region / Unit / Orders tabs.
  • The units dock stays the bottom sheet's fourth tab.
  • Header collapses to project and turn only.
·

Choosing between them

All four satisfy the six requirements in the issue and all four are built from the same shared React components, so native and web stay identical in every case. The differences that actually matter:

Pick 01 if

  • Familiarity to existing Atlantis players is the priority.
  • You want a fixed grid where nothing ever overlaps the map.
  • You want the shortest path from picking a unit to writing its orders.

Pick 02 if

  • You never want a widget hidden or collapsed.
  • Report and turn history deserve a permanent home.
  • You value the simplest thing to build, resize and test.

Pick 03 if

  • The map is the thing you stare at, and everything else is a lookup.
  • You are happy with a narrow, 3–4 column unit table.

Pick 04 if

  • You want the full map and the full-width unit table.
  • You want to open the map right up on demand without a layout change.
  • Phone and tablet use is a near-term goal.

Recommendation: 04, Docked Inspector. It resolves the tension that made 01 and 03 each imperfect. 03 gave the map the whole window but starved the unit table; 01 gave the table its full width but permanently spent a third of the window on chrome. 04 gets both, because the table is an overlay that collapses rather than a fixed row — and moving report state into the header removes the one panel that never needed map-adjacent space. The cost is four collapse states to persist and test, and panels that overlay the map they describe. If you would rather never have a panel cover a hex, 01 remains the conservative pick.

Note on scope. These are layout proposals, not a visual style guide. Colour, spacing and type in the real build come from Tailwind tokens as specified in docs/implementation-plan.md; light and dark themes are issue #9's scope. The hexes here are drawn as SVG for the mockup — the real map stays on PixiJS.
