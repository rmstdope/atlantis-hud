What the server said went wrong — proposals (bead ah-58dz)

Psylocke found this on a real send to the live server while verifying ah-etb0.2, which passed. Send a turn with a mistake in it and the dialog tells you, in full: “1 error found!” — and nothing else. Not which order, not which unit, not what was wrong with it. So you go back to the server's web interface to read what the application already received and threw away.

§1  Why it happens, and why the obvious fix is forbidden

serverErrorReport reads only the tail of the echoed block, after the last #end. But the server does not put its errors there. It echoes your document and annotates it inline, immediately above the offending line. Everything useful is before #end; only the summary count is after it.

#atlantis 95 "swordfish" <- the password. Must never reach the screen. unit 803 FORM 5 STUDY FORC *** Error: xNAME is not a valid order. *** xNAME UNIT "Scouts" CLAIM 895 END #end <- everything above this line is thrown away today 1 error found! <- this, alone, is what you are shown
So it is not reading too little — it is reading the wrong region. And widening it to the whole block is precisely what the password rule forbids: the #atlantis line, with the faction password in it, is the first line of that block.
But the password defence is already stronger than that comment suggests. The code does not rely on “start after #end”. It already filters every line against /^\s*#atlantis\b/ positively, and its own comment says why: “a document holding a second faction block, or one missing its final #end, puts an #atlantis line after the last #end. Dropping the header positively is what actually keeps the password out of what a player sees.” Applying that same filter to the wider region is safe, and it answers the bead's own open question: it matches the directive by name, so a leading blank line cannot defeat it.

§2  How much of your own document to show the real dialog, at its real 26rem width

A The error lines only

Every line matching *** Error: … ***, and nothing else.

Send orders to the server

Borg TNG (95) · turn 71 · atlantis-pbem.com

Turn 71 sent.

The server reported 
*** Error: xNAME is not a valid order. ***
Close
  • Smallest possible exposure of the document.
  • Says what was wrong.
  • Still does not say which order or which unit. With three identical errors you get three identical lines.

B Error, the order, and the unit

Each error, the line beneath it, and the unit line the error falls under.

Send orders to the server

Borg TNG (95) · turn 71 · atlantis-pbem.com

Turn 71 sent.

The server reported 
unit 803
*** Error: xNAME is not a valid order. ***
  xNAME UNIT "Scouts"

1 error found!
Close
  • Everything needed to go and fix it — the unit, the order, and the complaint.
  • Scales: three errors in three units read as three small blocks.
  • Keeps the summary count as a last line.
  • More of the document on screen, and it needs a rule for "the enclosing unit line".

C The whole echo

Everything the server sent back, with every #atlantis line filtered out.

Send orders to the server

Borg TNG (95) · turn 71 · atlantis-pbem.com

Turn 71 sent.

The server reported 
unit 803
FORM 5
  STUDY FORC

*** Error: xNAME is not a valid order. ***
  xNAME UNIT "Scouts"
  CLAIM 895
END
#end

1 error found!
Close
  • Cannot miss anything, whatever shape the server's reply takes.
  • Simplest rule, so the least to go wrong if the server reformats.
  • A real turn is hundreds of lines. The box is 7rem and scrolls, so one error means hunting for the highlighted line by scrolling — which is close to the problem being fixed.

§3  The safety rule, whichever is chosen

Every line shown is filtered against /^\s*#atlantis\b/, wherever it appears — not just the first line, and not just after #end. That is what already protects the tail today, and it is what has to protect the wider region. A test should send a reply with an #atlantis line in the middle of the block, after a blank line, and with leading whitespace, and assert the password appears nowhere in the result.
