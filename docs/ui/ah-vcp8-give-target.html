ah-vcp8 — One item resolver, and the give that lands nowhere

An order's item argument is resolved three different ways by three functions that search different places, so the same legal order can move men in one column of a row and not in another. Measured by reading the code on ae426d8, on a two-unit hex holding 8 orcs [ORC] and 8 leaders [LEAD].

Decisions (recorded from the planning discussion, navigator, 2026-08-29). The bead is split: ah-vcp8.1 is the spelling half — one resolver, searching the catalogue and the holdings spelling by spelling, used by all three surfaces; it needed no decision from the navigator and changes no word on screen. ah-vcp8.2 is the target half and carries the three answers below. Both were kept in the same epic rather than one being deferred.

1. A unit number the report names nowhere: the order does nothing — no charge, no credit, no doubt marker (reading A). Rejected: charging the giver, which is alarming and wrong when the player simply mistyped a number; and showing ? with a doubt marker (reading C), which was offered and set aside.
2. A unit the report does show but we cannot project — an ally standing here, or FACTION 2 NEW 1: the goods leave, and no row of ours gains them (reading D). Rejected: leaving both alone (reading E), which would show a player still holding ten swords they have given away.
3. No new wording either way. The ITEMS cell's own was: tooltip carries it.

The question — GIVE 999 ALL ORCS, where 999 is not in this hex

This is the second half of the bead, and it is a different question from spelling. The two sides already disagree on purpose, each for a stated reason:

  • The preview treats it as void. effects::give returns early when the target is not a row in this hex, so nothing leaves the giver.
  • The ledger charges the giver anyway. Its own comment says so in as many words: "a gift out of the hex is charged to the giver and credited to nobody."

Neither is obviously wrong. rules/give: "A unit may only give items, including silver, to a unit which it is able to see, unless the faction of the target unit has declared you Friendly or better." A unit we cannot see may still be standing there — stealth is a skill — and if it is, the goods really do leave. So the ledger is being pessimistic on purpose, and the preview is being literal about what it can see.

Round 2 — the third case, found while working out how to implement reading A

"A unit this hex does not show" turns out to be two different things, and the code has to branch on both. hex.units holds own units only (.filter(|unit| unit.own)), so today's "not found" arm catches an ally's unit standing right beside the giver as well as a unit number that appears nowhere. The effects walker already keeps the two apart — known_units is "every unit id the report names, ours and everyone else's", and TRANSPORT already uses it — but GIVE does not.
