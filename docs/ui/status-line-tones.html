ah-9gk — the header status line as one message channel

Decision (2026-08-16): Q1 → A, a visible notice tone with a dim grey dot; Q2 → the tone table as proposed (comparison failures become failures, “stored for history” becomes a notice); Q3 → 3-i, a failure never hides the turn-messages chip.

Today the header's status line is an ImportStatus — the counts of the last import plus two flags — and it is the shell's only way to say anything to you. A message is visible only when it is flagged failed or warning; anything else is written but hidden (screen readers and the test suite still read it). So every unrelated message has had to pose as an import warning to be seen, and two — “orders imported: 3 units”, “merged 3 regions from …” — ship invisible today. The refactoring gives the line a small message type with a tone, and the header decides visibility from the tone alone. Nothing about the header's layout moves; the only thing you can see change is which lines appear and in what colour. Three questions below.

Question 1 Should there be a visible “notice” tone, and how does it look?

Warning (amber dot) and failure (red dot) are as today. The open question is the middle tier: a line worth a glance that is neither — “orders imported: 3 units”, “merged 3 regions from Borg (73), turn 71 — 2 new to your map”, “turn 70 stored for history; still showing turn 71.” The routine counts (“11 regions · 42 units”, “restored turn 71”) stay hidden in every variant — that was decided on 2026-08-11 (“drop routine chatter from the title bar”) and is not re-opened.

A Notice, dim dotRecommended

A visible line with a neutral grey dot, same weight as a warning. Reads as “something happened”, not “something is wrong”.
Game Borg ▾Turn 71▾ orders imported: 3 units 2 events▾ImportExport ▾
Game Borg ▾Turn 71▾ merged 3 regions from Borg (73), turn 71 — 2 new to your map 2 events▾
  • “orders imported” and “merged …” become visible, as ah-470 and the merge flow intended
  • three tones, three dots — one rule to learn
  • a third colour of dot in a header that already has two

B Notice, green dot

Same line, but the dot is the success green already used elsewhere. Reads as “done”.
Game Borg ▾Turn 71▾ orders imported: 3 units 2 events▾ImportExport ▾
Game Borg ▾Turn 71▾ merged 3 regions from Borg (73), turn 71 — 2 new to your map 2 events▾
  • green / amber / red is a scale everyone already knows
  • “stored for history; still showing turn 71” is not a success — green would say the wrong thing about it
  • a green dot invites the eye to a line that mostly does not need it

C No notice tier — quiet stays quiet

Only warning and failure are ever visible; notices are written for screen readers only, exactly like the counts. Today's rule, kept honestly.
Game Borg ▾Turn 71▾ orders imported: 3 units 2 events▾ImportExport ▾
Game Borg ▾Turn 71▾ merged … 2 events▾
  • the header stays as quiet as it is today
  • “orders imported: 3 units” — the one confirmation an orders import gives — stays invisible
  • “stored for history” must then stay a warning to be seen at all, which is the lie the bead is about

Question 3 Does a failure still hide the turn-messages chip?

Today a failed status also hides the “2 events / 1 error” chip beside it, on the reasoning that a failed report load leaves the previous turn on screen and a chip counting that turn's messages next to a line about a different file could mislead. The same rule fires for “could not plan a route”, which is why the comparison failures were filed as warnings — to keep the chip. Three ways to settle it:

3-i Never hide itRecommended

The chip always counts the turn on screen, which is exactly the turn on screen. A failure line beside it says what failed.
Game Borg ▾Turn 71▾ could not read turn72.txt: no faction header ⚠ 1 error, 2 events▾
  • one rule: tone decides the line, nothing else moves
  • comparison failures can be honest failures
  • the chip's numbers sit next to a line about a file that never loaded

3-ii Hide it only when a report failed to load

As today for “could not read …” and a failed restore; every other failure (route, orders import, comparison) leaves the chip alone.
Game Borg ▾Turn 71▾ could not read turn72.txt: no faction header ⚠ 1 error, 2 events ▾
Game Borg ▾Turn 71▾ could not plan a route: no path ⚠ 1 error, 2 events▾
  • keeps the original worry covered
  • a second flag on the message (“this was the report”) — the thing the bead calls a hidden rule

3-iii Any failure hides it (today)

Unchanged behaviour: red line, no chip, whatever failed.
Game Borg ▾Turn 71▾ could not plan a route: no path ⚠ 1 error, 2 events ▾
  • nothing a player has seen changes
  • the comparison failures stay filed as warnings, or start hiding the chip — the exact cost the bead names

Unchanged What is not being asked

The line's place in the header, its wrapping on a narrow window (it is one flex item and wraps with the rest, as it does now), that a message stays until the next one replaces it (no timers), that “no report loaded” is written when there is no turn, and that the routine counts stay screen-reader-only. All as today.
