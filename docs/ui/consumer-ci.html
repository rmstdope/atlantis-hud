Proving the harness works somewhere it has never been

Nothing anywhere exercises cerebro as a consumer's submodule. Its CI runs the suites in place, so the mount point, the tracker's program name, the default branch and the install step are all invisible to it — which is why none of the coupling the sibling beads found was noticed. This bead builds one CI job that stands up a consumer deliberately unlike this project and drives the fleet against it.

The fixture is not a new invention: four bash suites already fabricate consumers under mktemp -d, and an ERT test already symlinks .claude/cerebro into a temp directory. Generalising those is the missing piece.

The bead's own recommendation cannot be taken literally. It says to build the job red and turn it green as the siblings land, because that "makes every sibling's definition of done mechanical". But nothing merges red — a failing job blocks every pull request in the repository until the last sibling lands. That is the whole fleet stopped for days, to gain a checklist. So the question below is really: how do we keep that property without the blockage?
