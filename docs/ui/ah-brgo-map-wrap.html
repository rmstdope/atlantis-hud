ah-brgo — making the map view wrap east–west

Found verifying ah-0w7w: a game whose map is set to wrap still scrolls past x=0 to the left and past x=71 to the right. The flag is recorded, the movement planner honours it — the map view has never seen it.

"THE MAP DOES NOT WRAP EAST-WEST even with the setting turned on. Scrolling continues past x=0 to the left and past x=71 to the right, so the wrap flag is recorded but the map view does not honour it."

Two facts shape every answer below. The map is one SVG group with one transform, drawn once — 1601 lines, a dozen render passes, nothing repeated anywhere in the app. And nothing in the view layer knows the map's width: the shape reaches only four core calls as a JSON string, never the canvas.

So "make it wrap" has three quite different meanings, at very different costs. The strips below show the same pan, east, past the seam.

Chosen the map repeats — a true cylinder

Decided 2026-08-22: option A, over a bounded pan and over a jumping camera, and over shipping the cheap version first. B and C are kept below with the reasons they were not taken.

A note on the cost. The question was asked with "every render pass emits three copies" as the price. Planning afterwards found a cheaper implementation that delivers the same thing: the world is drawn once into a group with an id, the ghosts are SVG <use> elements referencing it (two DOM nodes, not two copies of everything), and the camera's translation is folded modulo the world width after every pan so one ghost each side is always enough however far you drag. The fold is invisible, because at the moment it happens the ghost under the pointer is pixel-identical to the real world replacing it. So the cost accepted here is larger than the cost actually being paid.

A The map repeatsChosen

The world is drawn three times — at x−W, x and x+W — so panning east runs continuously into a second copy. Truly cylindrical.
panning east …
… keeps going, into a second copy
  • The only option that is actually a cylinder: a hex on the seam has its true neighbours drawn beside it.
  • Matches what the movement planner already believes about the world.
  • Every render pass emits three copies — terrain, roads, provinces, routes, marks, notes, rings, the hit layer. Three times the SVG nodes on the biggest component in the app.
  • Every click must fold x back into range, or clicking a ghost selects a hex that does not exist.

B Panning stops at the edge

No repetition. The camera simply cannot pan the world off screen — the eastern edge stops where the map ends, as it does in most map tools.
panning east …
… and stops, with the edge at the edge
  • Fixes the reported symptom exactly — you can no longer scroll into emptiness.
  • One change in mapViewport.ts; the renderer is untouched, so no performance cost and no click-folding.
  • Works for a non-wrapping map too, where scrolling into the void is equally pointless.
  • Not a cylinder. A hex at x=71 still looks like an edge, though its eastern neighbour is x=0.

C The view jumps round

Pan past the seam and the camera teleports to the other side — the same world, re-entered from the west. No repetition drawn.
panning east, about to cross …
… and the view is suddenly at the west edge
  • Cheap like B, and every hex is reachable by panning in one direction.
  • The jump is the problem. Content leaps sideways under a dragging pointer, which reads as a glitch rather than a world.
  • Worst of both: neither continuous nor bounded, and it still needs the width threaded in.
Whichever is chosen, the same plumbing is needed first: the map's shape has to reach MapCanvas, which it never has. That part is not in question.

Chosen Odd map widths — the lattice does not join

The hex lattice only holds positions where x + y is even. A map 72 wide joins cleanly: x and x+72 have the same parity. A map 71 wide does not — the rows on one side of the seam sit half a hex above the rows on the other, so the two edges genuinely do not meet.

#Behaviour when the width is oddNote
2-iDo not wrap the view; treat it as a non-wrapping mapDone here, defensively — a game saved before the refusal exists may already carry the combination.
2-iiWrap anyway and let the rows sit half a hex outVisibly wrong at the seam, and clicks near it would land on the wrong hex.
2-iiiRefuse the setting at the point it is enteredChosen — the navigator's words were "we should not allow odd width and x wrap; the same for odd height and wrap y". Filed as ah-teg0, blocked on ah-0w7w because it changes forms still being fixed.
Atlantis' own maps are even-width (the ruleset default is 72), so this is a guard rather than a common case. It matters because the setting is free text.

Chosen North–south

wrapY exists, is honoured by the movement planner, and the ruleset default is false — an Atlantis map has poles. The question is only whether the view should treat it the same way as wrapX.

#BehaviourNote
3-iSame rule, both axesChosen. One rule, no special case, and the view never disagrees with the movement planner.
3-iiEast–west only; north–south always just stopsFewer moving parts, and matches the ruleset default — but it means the view disagrees with the movement planner on a map that does wrap north–south.
