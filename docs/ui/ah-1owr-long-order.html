The Long order column — where it sits, and what it says

A ninth column on the units-in-hex table saying what each of your own units will actually spend the month doing: whichever of ADVANCE BUILD ENTERTAIN MOVE PILLAGE PRODUCE SAIL STUDY TAX TEACH WORK its orders carry. Read live from the orders document, so editing an order changes the table.

Three things the contributor's branch decided by default, which are yours rather than theirs: where the column sits, whether it sorts, and how the order is written out. Everything else about this column was already settled in review — an own unit with no long order shows a red em dash, and someone else's unit shows nothing.

Rows below are real orders from the fixture report: produce yew, @tax, @study stea, MOVE SW, and one own unit given nothing.

2 · How the order is written out

Orders are typed by hand, so the document holds whatever case the player used, @ included. Three rows here are the same three units.

iExactly as typed

The line straight from the document, trimmed and no more.
WoodsmenYproduce yew
Taxers@tax
Landlord@study stea
Lone RiderMOVE SW
  • Truthful — it is what is actually in the file
  • A ragged column: case and @ vary row to row for no reason the reader cares about

iiUpper-cased, @ kept

The whole line normalised, so the column is uniform but nothing is dropped.
WoodsmenYPRODUCE YEW
Taxers@TAX
Landlord@STUDY STEA
Lone RiderMOVE SW
  • Scans cleanly down the column; the @ still marks a repeating order
  • Matches how the rules and the order help write commands
  • Not byte-for-byte what the player typed, which this app is otherwise strict about

iiiThe command only

Just which of the eleven it is, dropping the arguments.
WoodsmenYPRODUCE
TaxersTAX
LandlordSTUDY
Lone RiderMOVE
  • Narrowest by far, and groups perfectly if the column ever sorts
  • Loses what is being produced, studied or where it is moving — often the point
