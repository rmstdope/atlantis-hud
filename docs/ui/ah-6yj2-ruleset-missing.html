ah-6yj2 — every unit shown as an estimate

The bead assumes a parser defect. It is not one. Measured against the fixture you loaded:

units in the report            372   (182 your own, 190 foreign)
units that state what they hold  372   - every single one
item tags used by those units   all known to the ruleset (171 tags, 0 unrecognised)

And the classifier clears the estimate flag whenever it recognises everything a unit holds. So with the ruleset loaded, none of those 372 units should be an estimate — own or foreign. There is no separate rule to establish for foreign units in this report, because not one of them conceals its composition.

What actually happened is that the classification never ran. It only runs when the ruleset is loaded:

ruleset "ready"        -> parseReportClassified   -> men counted, flag cleared
ruleset anything else  -> parseReportFull         -> every unit an estimate

There are three ways to be in the second row: the report was loaded before the ruleset finished fetching; the fetch failed; or the game's ruleset has no file at all. All three are silent. `RulesetState` has had an unavailable case since it was written and nothing in the interface has ever mentioned it — no banner, no status line, no chip. The app simply degrades every number in the report and says nothing.

So the questions are not about the parser. They are about what should happen when the rules are not there.

Chosen a load waits for the ruleset

Decided 2026-08-23: 1-i, once it was established that the ruleset is a local bundled asset rather than a network call — /ruleset.json, served from config/public by the build, working offline. The navigator's condition was exactly that, and it holds.

The navigator also corrected the bead: every unit, not nearly every, and in a browser. That is the decisive detail, because it is the signature of the classification pass not running at all rather than of any rule about which units can be estimated.

The fetch takes a moment. Import a report inside that moment and you get the unclassified parse — permanently, for that load. This is the likeliest cause of what you saw, because you opened the app and loaded a fixture straight away.

1-i Wait for itChosen

A load that arrives while the ruleset is still loading waits for it, then parses classified.

  • Removes the race outright rather than reporting it.
  • It is a local file behind a fetch — the wait is imperceptible in the ordinary case.
  • If the fetch is slow or hangs, the import appears to hang with it, so it needs a ceiling.

1-ii Parse now, reclassify after

Load immediately; when the ruleset arrives, re-parse and replace the figures.
  • Nothing ever waits.
  • Numbers change under the player a second after they appear, which is its own kind of wrong.
  • Two parses of a large report for every load.

1-iii Refuse until it is ready

The Import control is disabled while the ruleset is loading.
  • Honest and simple.
  • Disables the app's main action for a moment on every open, for a case that resolves itself.

Chosen when the ruleset genuinely is not there, say so

Waiting cannot help this one: the fetch failed, or the game names a ruleset with no file. Today the report loads, every unit becomes an estimate, and nothing is said. Whatever is chosen here is the first thing the interface has ever said about a missing ruleset.
