Resizable columns — and the defect this must not repeat

A splitter at each boundary between two headers; dragging moves width from one column to the other. Widths persist. That much is straightforward and PR #421 already has it working.

What went wrong on that branch, precisely. The drag itself is sound — dragColumnBoundary keeps left + right constant, so a drag can never change the table's total. The loss comes from somewhere else: the stored widths are pixels totalling 1132px, while the table is w-full table-fixed inside a box whose width is the window minus both rails — each of which the player can drag between 12 and 45rem. When that box gets narrower than the total, the rightmost columns are laid out past the edge, and the container's overflow-x-hidden clips them with no scrollbar to bring them back.

So widening a rail can lose a column, and nothing the player does to the table can recover it. Both answers below fix that; they differ in what happens to your chosen widths when the space changes.

2 · The two answers

Both make the loss impossible. The difference is what your chosen widths do when the space changes.

AWidths are shares of the table, not pixels

A column stores what fraction of the table it owns. The table is always exactly 100% wide, so the columns can never total more than it — the overflow is not prevented, it is impossible. Narrow the window and every column shrinks in proportion, keeping the shape you chose.

  • A column cannot be lost, by any sequence of drags, rail moves or window sizes — it is arithmetically impossible, not merely bounded
  • The shape you chose survives every resize, proportionally
  • Nothing new on screen: no scrollbar, no reflow, no jump
  • A very narrow window makes every column narrow; nothing stays legible by choice
  • A minimum width in pixels can only be honoured approximately, since a share is not a pixel

BPixels, and the table scrolls sideways when it must

Columns keep the exact pixel widths you gave them. When they no longer fit, a horizontal scrollbar appears and you scroll to the rest — a real Windows-Explorer table.

  • A horizontal scrollbar in a pane that has never had one, under a list that already scrolls vertically
  • You can still end up scrolling to see a column, which is the annoyance the defect was about

3 · Where the reset lives

Whatever else, a player who has made a mess needs a way back. Double-clicking one boundary already resets that pair — this is the control that restores all the columns. The app has no reset control of any kind today, so this is a new thing wherever it goes.
