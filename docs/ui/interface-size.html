An Interface size setting — what the player sees (bead ah-46p.2)

ah-46p.1 merged this morning: the panes' six hard-coded pixel sizes became three rem tokens — --text-pane-sm 11px, --text-pane 12px, --text-pane-lg 13px at a 16px root — so a reader who raises their browser's font size now sees the panes grow. This bead adds a control inside the app, for the reader who would rather not change their browser, or who wants the panes bigger and the rest of the web left alone.

The map is safe, and that is not luck. Every piece of map text carries its own explicit size — SVG fontSize numbers, or px in the theme stylesheets — and theme.css says so in as many words: “The map sets its own sizes and is not on this scale.” Scaling the three tokens cannot reach it.

Decided, 2026-08-17. (1) A slider, 100% to 200% in steps of 25%, in the Global tab directly beneath Pane transparency — the same primitive, one field down. (2) Row heights follow the text, so nothing clips at any offered size; pane widths stay as the player dragged them. (3) The default is 100% — nothing changes for anybody until they ask — and the hint line ships verbatim: “Makes the panes, the header and the dialogs bigger. The map is not affected.”

The control Option A was chosen

OPTION A — chosen A slider, like Pane transparency

The Global tab already has one — Pane transparency, a range from 0 to 95 in steps of 5. An Interface size slider sits directly beneath it and needs no new kind of control.

100% to 200%, in steps of 25%. The map is not affected.
  • Matches a control that is already there, one field below.
  • A percentage is a thing readers understand from every other application.
  • A slider invites values between the useful ones; the steps are what stop that.

OPTION B — rejected Named steps

Four buttons, in the shape of the existing Dark/Light theme control on the same tab.

Interface size
The map is not affected.
  • Only sensible values are reachable, and each has a name.
  • Reads faster than a number when you are choosing rather than tuning.
  • Four words for four numbers, and “Largest” is a poor name for 200%.
  • Does not say how much bigger, so a reader cannot tell what they will get.
The hazard, found by measuring rather than by guessing. The unit table's rows are a fixed 22 pixels (unitTable.ts:11, applied as an inline style because the table is virtualised — every row must be the same known height for the scrolling to work). At 100% the row holds 11px text comfortably. At 200% it holds 22px text in a 22px box. A smoke test pins that height exactly (workspace.spec.ts:2299), so this is not a thing that can be left to chance — question 2.

What else moves with the text Option 1 was chosen

OPTION 1 — chosen Row heights follow the text

The unit table's row height becomes the scale times 22, so the text always has room. The panes' widths do not change — the player already drags those, and overriding a width they chose would be worse than leaving it.
