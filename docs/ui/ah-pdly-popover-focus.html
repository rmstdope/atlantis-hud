ah-pdly — where focus goes when a popover opens

Every header popover is a role="dialog" with an aria-label, and none of them moves focus when it opens. So a keyboard or screen-reader user presses the chip, is told a dialog opened, and is then left standing on the chip with no indication of where the dialog is. It works only because the panel happens to follow the chip in the DOM, so Tab reaches it next.

The bead says three panels. It is eleven, and they all share one frame:

That is good news rather than bad: PopoverFrame is the common root, so this is one change in one file and all eleven inherit it. The question is only what receives focus. ImportSummaryDialog already solves the same problem by autofocusing its close button, so the pattern exists in the codebase — it is the popovers that never adopted it.

Chosen the panel itself takes focus

Decided 2026-08-22: option A, and on close focus returns to the chip in every case — Escape, the ✕, a press outside, and after choosing something in the panel. B and C are kept below with the reasons they were not taken.

Chosen where focus goes when it closes

Closing has to put focus back or the user is dropped on <body> and has to tab from the top of the page. Today the panel simply unmounts. One rule, no exceptions — the alternative offered was to leave focus alone after choosing something, and it was rejected because that is the case where a keyboard user most needs to know where they now are.

Closed byProposed
Escapeback to the chip that opened it

One rule, no exceptions: focus returns to the chip in every case. The alternative — leaving focus wherever the click landed — is what browsers do by default and is why a dialog that does not restore focus is considered broken.
