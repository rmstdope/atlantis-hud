ah-kjfm — the fifth sweep

A bead reopened by a failed verification comes back status=open — no lease — but still naming its old assignee. Every implementer then walks past it. Twice on 2026-08-23, both times a P0, both times found only because a planner read bd ready by hand.

P0 ah-fjty  assignee=Cyclops  — Cyclops was building ah-gjq4
P0 ah-t2pn.3  assignee=Wolverine  — Wolverine was building ah-1ad6.1

It strands the highest-priority work specifically, because the reopen path is where it happens and a reopened bead is P0 by definition.

Does it act, or ask?

sweep-claims.sh's header states the invariant plainly: the scripts never mutate, and “a human confirms every one of those decisions before anything destructive runs”. cerebro--finding-command is “the complete list of destructive commands the fleet view can run”.

1 — confirm, like the other fourA Sweeps line and a key that clears it on confirmation. Keeps the invariant exactly, and every destructive path stays in one auditable list. But the failure is that nobody was looking — a line nobody presses strands the P0 just as silently.
2 — clear it automatically, and reportNothing is destroyed: the lease is already gone and no work is taken off anyone, so this is closer to tidying than to bd close. Costs the invariant its simplicity — the sweep becomes the one that writes without asking.
3 — confirm, but make it shoutConfirmed like the rest, except a stranded P0 also raises the same alert the fleet view already uses for a session that is asking. Keeps the invariant and fixes the not-looking problem for the case that matters.
