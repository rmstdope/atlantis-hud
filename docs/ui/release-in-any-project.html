Cutting a release — in a project that is not this one

Cerebro's release procedure (agents/orchestrator.md) is shared by every project that uses this harness, and three parts of it are about Atlantis HUD specifically: it runs pnpm run release <bump>; it describes the gate as "lint, typecheck, unit tests, rustfmt, clippy, rust tests"; and after the tag it watches a GitHub Actions workflow literally named Release that "builds the macOS bundle".

ah-qled.1 already built the mechanism and the key is already declared — .claude/cerebro-project.conf carries release_cmd  pnpm run release today. So the first of the three is settled and is not asked about below.

# .claude/cerebro-project.conf, already on main
project_name Atlantis HUD
default_branch main
install pnpm install --frozen-lockfile
release_cmd pnpm run release

What is left is the part that is not a command: "there is a build to watch after tagging" is an assumption, not a fact. A consumer with no release workflow should not be told to watch one.

1 · How Cerebro knows whether there is a build to watch

AA declared workflow name

A new release_watch key names the workflow. Absent means there is nothing to watch, and Cerebro says the release is done at the tag.
release_cmd pnpm run release
release_watch Release
this project:
v0.11.0 tagged. Watching the
Release build ...
done - the macOS bundle is up.

a consumer with no workflow:
v2.3.0 tagged and pushed.
Nothing further to watch.
  • Explicit: the consumer says whether there is a build and what it is called
  • Same pattern as every other project fact, in the file that already exists
  • One more key to declare, and a consumer who forgets it is told nothing is watched when something is

BLook and see

After the tag push, ask GitHub what started. If a run appeared, watch it, whatever it is called; if nothing did within a short window, say so and stop.
$ gh run list --limit 1 \
    --json databaseId,name,createdAt
started since the tag?
yes - "Publish" #4821
watching ...

a consumer with no workflow:
nothing started in 60s -
v2.3.0 tagged and pushed.
  • Nothing to declare, and it is right on the first release rather than the second
  • Works for a workflow whose name nobody remembered to update
  • A slow-starting workflow looks like no workflow — a timing guess in a release
  • Could latch onto an unrelated run that happened to start just then

CAsk the navigator

After the tag, Cerebro says the tag is pushed and asks whether to watch a build — offering what it can see in gh run list.
v0.11.0 tagged and pushed.

Two runs started just now:
  1 Release  #4821
  2 Docs     #4822
Watch one, or stop here?
  • Never wrong, because it never guesses
  • A question in the middle of a release you already asked for
  • Cerebro is meant to relay a release, not conduct an interview during one

2 · The gate description, and the release script's own flags

The prose says the gate is "lint, typecheck, unit tests, rustfmt, clippy, rust tests" — half of which is Rust, which most consumers will not have. It also names --allow-any-branch and --dry-run, which are flags of this project's release script and may not exist in another's.

iSay what it is for, not what it contains

"runs the project's full gate before it touches anything, so expect it to take several minutes." The flags move to a sentence saying a project's release command may offer a rehearsal, and to ask rather than assume.
Cerebro, in any project:
Running pnpm run release minor.
It runs the project's full gate
first, so this takes a few minutes.

(a rehearsal, if the command offers
 one, only when you ask for it)
  • True in every project, and still tells the navigator why it is slow
  • Nothing to keep in step with a gate that changes
  • Loses the detail that made a gate failure easy to place

iiKeep the detail, as this project's example

The generic sentence, followed by "in Atlantis HUD that is lint, typecheck, unit tests, rustfmt, clippy and rust tests" marked plainly as an example.
Cerebro, in any project:
Running pnpm run release minor.
It runs the project's full gate
first — here that is lint, typecheck,
unit tests, rustfmt, clippy and
rust tests — so this takes a few
minutes.
  • Keeps the concreteness that makes a failure easy to place
  • A named example of one project inside a shared file is the thing this epic is removing
  • Goes stale the day this project's gate changes, silently
