# Review of PR #1166 — bead ah-j9wn (reshape magic study plans)

Reviewed `5ce383f6` (worktree at that sha; `check:fast` passes; 106/106 shared unit tests pass; new smoke test passes on both `web` and `desktop-shell` projects).

**What this does well** — a faithful implementation of the bead. The pure helper sits in `packages/shared/src/studyPlans.ts` on top of `plannedGoals` rather than re-implementing its sanitation; the store action is one queued, write-first `saveStudyPlans` of every cached row with the cache updated only after success; the copy in `scheduleConfirmCopy` is the agreed `acceptance` text verbatim; the dialog is a separate hook-owning layer so `ScheduleGrid` stays statically renderable; and the focus-return convention is honoured on every close path. Comments explain the *why* in this repository's style throughout.

## Findings

1. **minor** — `packages/shared/src/workspace/StudySchedule.tsx:1176` (`ScheduleConfirmDialog`): the overlay is `aria-modal="true"` but has no focus trap, so `Tab` walks into the schedule behind the dialog. The bead does not require a trap and the planner's other nested surfaces behave the same way, so this is a suggestion, not a blocker — but if the planner ever grows a trap, this dialog should get it too.

2. **minor** — `packages/shared/src/workspace/StudySchedule.tsx:1230` (`ScheduleConfirmLayer`): opening focus is taken by `document.querySelector('[data-confirm-action="…"]')` from a global effect rather than a ref on the dialog's own button. It is unambiguous today (only one such dialog can be mounted), but a ref would be immune to a second mounted dialog and costs nothing. Suggestion.

3. **nit** — `packages/shared/src/workspace/StudySchedule.tsx:1172`: the action button carries both `data-testid="study-schedule-confirm-action"` and the duplicate `data-confirm-action="study-schedule-confirm-action"`. The second exists only for the focus effect; a ref would make it redundant (see 2).

4. **nit** — `tests/smoke/study-planner.spec.ts` (~line 755 comment): the comment's arithmetic walkthrough of the two confirmed operations is correct against the assertions below it, but it is doing a lot of work to explain a single test; if this scenario grows, splitting insert and remove into two tests would read better. Not requested by the bead.

## What I verified

Insert shifts goals at/after the target one turn later and keeps the rightmost goal off-horizon rather than dropping it (`reshapeStudyGoals`, tested explicitly); remove drops the target and shifts later goals earlier; every cached plan is written in one `saveStudyPlans` call with `[]` removals and the cache is replaced only after the write succeeds; the confirmation dialog is between the header control and any write, and only its action button invokes `onScheduleChange`.
- **Copy**: the insert heading, remove heading, remove explanation, action labels and Cancel match the bead's `acceptance` field exactly; the insert explanation is the one the plan records as decided.
- **Architecture**: helper in `packages/shared/src/studyPlans.ts`, action in `studyPlansStore.ts` queued through the existing `queued` helper, callback wired `AppShell → StudyPlannerDialog → StudySchedule` exactly as planned, with the exact error copy `Could not reshape this schedule.` and the no-game guard preserved.

The unit tests assert behaviour, not implementation shape, and would fail against the old code.

- **Cost**: no new dependency, no CI change, no render-loop work; the helper is O(n) per plan row once per confirmed reshape.

**Recommendation** — no blockers. Merge as is; findings 1–3 are suggestions the implementer may decline.
